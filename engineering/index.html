How Perch is built

Perch holds a credential that can run shell commands on your machine. That is the whole reason for the care described below, and for publishing the list of things it still cannot do.

The API is measured, never assumed

An early draft of this project specified an entire API that did not exist — endpoints, headers, event names, all plausible, none real. The correction became the first rule: if a path is not in a captured response, it does not exist. Every endpoint Perch calls is recorded with the request that proved it, and the forbidden ones are in a list a linter enforces.

The rule earned itself twice more. A decision document once declared the headline feature — answering an approval from your phone — unbuildable, quoting upstream source accurately. One request to a live gateway refuted it in about ninety seconds, and the feature shipped. Later, attachments went out working for images and text and broken for PDFs, because two methods that both take a document turned out to take different parameters. A live probe found it; 951 passing tests and a green pipeline had not.

So a nightly job replays every documented impossibility against real gateway releases, and "impossible" needs a failed request rather than a careful reading.

Two transports, and a refusal to split the live path

The agent exposes two surfaces: an HTTP API with server-sent events that every user has, and an optional dashboard speaking JSON-RPC over a WebSocket. Perch streams from the first — tokens, reasoning, tool calls — and opens the second only while a file is actually moving, then closes it.

The dashboard also pushes session and message events, and Perch deliberately ignores them. Adopting them would give dashboard users one live path and everyone else another, and two code paths that drift is a worse product than one that is merely adequate. Attachments are the exception because there is no alternative: the surface every user has offers none, so the control is absent when no dashboard is paired rather than present and failing.

Offline is a design constraint, not a failure mode

  • An outbox that replays. Messages typed offline are queued and sent when the network returns.
  • Idempotent sends. Each carries a client-generated id, so a retry after a dropped response resumes the same run instead of starting a second one.
  • Cached transcripts, so opening a conversation on a train shows the conversation.
  • An approval sweep. A decision raised while the app was closed is recovered from the run id at next launch — the request expires in five minutes, so this is the difference between answering and losing the work.

Native where it counts, shared where it pays

Most of the app is one cross-platform codebase. Two things could not be, and are Kotlin modules behind interfaces: a foreground service that keeps a connection alive while you follow a run, and an Android 16 live-status notification. Platform branches are banned in product code and a linter enforces it — differences live behind the interface, so a capability that does not exist on a platform means the control is absent rather than present and inert.

The web build is the same code with real browser implementations of those seams, bounded by what a browser can honestly do: it persists no credential, because a browser has no keychain.

Battery and data are numbers, not intentions

63 budgets live in one config; 38 are graded against a measurement on every run. Seven are hard zeros — background wakeups, credentials in the JavaScript heap, bundled icon fonts — and a budget is not raised to make a build pass. Three of those zeros were enforced by nothing until a counting proxy started measuring them, which is the argument for measuring rather than asserting.

A crash that only appeared above a tablet breakpoint shipped once because every test ran at phone width. There is a flow at the other size now, and a negative control that must fail — a gate that cannot fail is not a gate.

Release engineering

Tag, and a pipeline runs the gates, builds an app bundle, a directly installable APK, an iOS simulator build and a web bundle, then drafts a release for a human to read. The APK's signing certificate is published and pinned: Android refuses an update signed by a different key, so a silent key rotation would permanently strand every sideload install. A changed fingerprint fails the build instead.

Over-the-air updates carry JavaScript only and the pipeline refuses to ship one if native configuration changed since the last tag, because that is the line store policy draws. Store submission is automated to a testing track; what cannot be automated — the listing, the declarations — is written down field by field so it is pasted rather than re-derived.

What it does not do

The list is public and kept current, because a client for a tool that can run commands should be legible about its limits:

  • It builds no servers. No relay, no account, no push infrastructure. Anything needing a backend is a stated limitation, not a roadmap item.
  • Attachments need a paired dashboard, because the surface everyone has offers none.
  • Nothing comes back to render for an attachment. A message row carries no media field, and inventing one would be the original sin above.
  • A private certificate authority is unsupported, and the app says so rather than failing obscurely.
  • Multi-device is a reconciling re-read, not a push. Named as the compromise it is.
